## 1. 결론

팀 인증, 부서 인증 같은 기준은 현실적이지 않다.

조직도 기준으로 과금하면 바로 문제가 생긴다.

| 문제 | 설명 |
| --- | --- |
| 팀/부서 경계가 애매함 | 실제로는 TF, 프로젝트, 현장, 본부, 외주 인력이 섞임 |
| 누가 팀인지 증명하기 어려움 | 구매 담당자도 "이게 팀 플랜인지 부서 플랜인지" 판단하기 싫어함 |
| 조직 개편 때마다 계약이 흔들림 | 부서가 합쳐지거나 쪼개지면 요금제도 애매해짐 |
| 사용자가 위축됨 | "이건 우리 팀 범위인가?" 같은 고민이 생김 |
| 영업 설명이 복잡해짐 | 가격표가 조직정치와 연결됨 |

따라서 Team / Department 요금제는 버리는 것이 맞다.

더 현실적인 과금 기준은 다음이다.

> 회사 내부망 1개 또는 고객사 1개 환경 단위의 플랫폼 라이선스 + 운영 용량 팩 + 보안/운영 옵션.

즉, 팀인지 부서인지 묻지 말고 이렇게 팔아야 한다.

> 고객사 내부망에 이 플랫폼을 깔아드립니다.  
> 앱 생성, 프리뷰, 내부 사용자는 제한하지 않습니다.  
> 대신 실제 운영 용량과 지원 범위에 따라 연간 계약합니다.

## 4. 제일 중요한 기준: 앱 개수가 아니라 운영 용량

앱 하나 만들었다고 돈을 받으면 안 된다.

하지만 진짜 무제한으로 전부 운영해주면 손해가 난다.

그래서 계약서에는 이렇게 넣어야 한다.

> 앱 생성과 프리뷰 배포는 제한하지 않습니다.  
> 실제 운영은 포함된 운영 용량 안에서 제공됩니다.  
> 지속적인 초과 사용이 발생하면 용량 팩 또는 상위 플랜으로 전환합니다.

즉, 과금 기준은 조직도도 아니고 앱 개수도 아니다.

과금 기준은 다음이다.

| 기준 | 이유 |
| --- | --- |
| 운영 리소스 | CPU, 메모리, 저장소, 로그, 실행 시간 |
| 운영 책임 | 모니터링, 알림, 장애 대응, 롤백 |
| 보안 책임 | 인증, 권한, 감사 로그, 데이터 접근 통제 |
| 배포 환경 | 고객사 내부망 1개, 전용 클러스터, 온프렘 |
| 지원 범위 | 기본 지원, 우선 지원, 전담 지원 |

## 7. 운영 namespace 자동 배포와의 관계

사용자가 바이브코딩으로 만들고, 자동으로 내부망 운영 namespace에 올라가는 구조라면 앱 카운팅은 더더욱 하면 안 된다.

대신 이렇게 관리해야 한다.

| 상태 | 과금 판단 |
| --- | --- |
| 생성됨 | 과금 안 함 |
| 빌드 실패 | 과금 안 함 |
| 배포 실패 | 과금 안 함 |
| 내부망에 올라감 | 바로 과금 안 함 |
| 프리뷰 URL 사용 | 과금 안 함 또는 기본 포함 |
| 실제 트래픽 발생 | 운영 용량 사용으로 계산 |
| 장시간 실행 | 운영 용량 사용으로 계산 |
| DB/파일/업무 API 연결 | 보안/운영 관리 대상 |
| 로그/모니터링 필요 | 운영 용량/옵션 사용 |
| 중요 업무로 지정 | 별도 운영 지원 대상 가능 |

핵심은 다음이다.

> 운영 namespace에 올라갔다는 사실이 아니라, 실제 리소스를 쓰고 운영 책임이 생기는지가 기준입니다.

## 11. 제안서에 넣을 요약 문구

MAEK의 가격 정책은 직원의 AI 활용과 바이브코딩을 위축시키지 않는 방향으로 설계됩니다.

앱 개수, 사용자 수, 팀/부서 단위로 과금하지 않고, 고객사 내부망에 설치되는 플랫폼 사용권과 실제 운영 용량 기준으로 계약합니다.

이 방식은 현업 직원의 자유로운 실험을 막지 않으면서도, 운영 리소스와 보안/지원 책임이 커지는 시점에는 용량 팩과 상위 플랜으로 확장할 수 있게 합니다.

따라서 MAEK은 "많이 만들수록 불리한 가격 구조"가 아니라, "많이 만들수록 조직의 생산성 자산이 쌓이고, 운영 규모에 맞게 자연스럽게 확장되는 가격 구조"를 지향합니다.
