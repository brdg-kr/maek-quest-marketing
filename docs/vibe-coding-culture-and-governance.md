# 바이브코딩 확산 이후의 조직 문화와 내부 개발 플랫폼 운영 모델

작성일: 2026-05-11  
대상 폴더: `D:\source\repos\brdg-kr\internal-dev-platform`  
문서 목적: 바이브코딩 확산으로 일반 직원이 직접 앱, 플러그인, 애드인, 웹서비스를 만들게 되는 미래를 가정하고, 회사가 어떤 문화와 운영 모델을 설계해야 하는지 정리한다.

## 1. 문제의식

AI 기술 발전으로 "개발을 모르는 직원"도 업무 도구를 만들 수 있게 되면서 회사의 소프트웨어 문화가 크게 바뀌고 있다.

예전에는 회사에서 필요한 플러그인, 애드인, 웹서비스, IT 서비스가 있으면 IT 서비스 부서나 외주사가 개발했다. 이제는 현업 직원이 AI를 이용해 직접 만들기 시작했다. 웹서비스, 플러그인, 애드인까지 개인이 만들 수 있다.

이 변화는 생산성을 크게 높일 수 있지만, 동시에 새로운 문제를 만든다.

예를 들어 같은 업무를 보는 직원이 50명 있다면, 50개의 비슷한 플러그인이 만들어질 수 있다. 기능은 비슷하지만 화면, 흐름, 계산 방식, 데이터 처리 방식이 조금씩 다른 도구가 50개 생기는 것이다.

현재는 로컬 CSV나 파일 데이터를 기반으로 한 작은 웹서비스나 자동화 도구 수준일 수 있다. 하지만 다음 단계에서는 직원들이 더 많은 데이터를 요구할 것이다.

> CSV 말고 실제 사내 데이터를 붙이고 싶다.  
> 고객 데이터, 프로젝트 데이터, 승인 데이터, 매출 데이터, 계약 데이터를 연결하고 싶다.

이때 기존 IT 서비스 부서는 더 이상 단순히 웹서비스를 만들어주는 부서가 아니라, 데이터 제공 서비스와 안전한 내부 개발 플랫폼을 제공하는 부서로 바뀌어야 한다.

핵심 질문은 다음이다.

- 50개의 비슷한 플러그인이 만들어지는 것이 회사 입장에서 맞는가?
- 그렇다고 50명이 합의해서 하나의 서비스를 만들라고 하는 것이 맞는가?
- 합의해서 하나를 만들면 정말 잘 굴러가는가?
- 그 방식은 과거 IT 부서가 하나의 애드인을 기획/조정/개발하던 방식과 무엇이 다른가?
- 그 다음 단계와 다다음 단계는 무엇인가?

## 2. 결론

회사는 50개의 비슷한 플러그인을 없애려고 하면 안 된다.

대신 다음 구조를 만들어야 한다.

> 50개가 생겨도 안전하고, 좋은 것은 자연스럽게 표준이 되고, 공통 부분은 재사용되도록 만드는 구조.

미래의 핵심은 하나의 정답 서비스를 만드는 것이 아니다.

핵심은 다음이다.

> 분산된 제작 + 중앙화된 데이터, 권한, 정책, 배포, 감사 체계.

한 문장으로 정리하면:

> 창작은 분산시키고, 신뢰는 중앙화한다.

## 3. 변화의 본질

과거 구조는 이랬다.

```text
현업이 요구사항을 정리한다
  -> IT 부서나 외주사가 만든다
  -> 배포한다
  -> 수정 요청이 쌓인다
```

현재 구조는 이렇게 바뀌고 있다.

```text
현업 직원이 문제를 느낀다
  -> AI에게 설명한다
  -> 직접 툴을 만든다
  -> 써본다
  -> 고친다
  -> 또 만든다
```

이 변화는 단순히 개발자가 줄어든다는 뜻이 아니다. 더 근본적으로는 소프트웨어 제작의 위치가 IT 부서에서 업무 현장으로 이동하는 것이다.

Google Cloud는 vibe coding을 코드 한 줄씩 직접 작성하기보다 AI에게 설명하고 생성, 수정, 디버깅을 맡기는 흐름으로 설명한다. 2026-05-11 기준 해당 페이지는 "프로그래밍 경험이 제한적인 사람도 앱을 만들 수 있게 한다"는 점을 강조하고, Karpathy가 2025년 초 이 표현을 만들었다고 설명한다.

이 변화의 장점은 속도와 접근성이다.

위험은 이해, 검증, 운영 책임이 약해지는 것이다.

## 4. 50개의 플러그인은 맞는가?

일부는 맞고, 일부는 틀리다.

맞는 부분은 이렇다.

50개의 플러그인은 낭비처럼 보이지만, 사실은 50개의 업무 해석, 50개의 작은 실험, 50개의 숨은 요구사항 발견이다. 기존 IT 방식에서는 이 미세한 차이가 요구사항 회의에서 사라졌다. AI가 개발 비용을 낮추면, 그 차이가 실제 도구로 표현된다.

틀린 부분은 이렇다.

50개의 플러그인이 각각 다른 데이터 정의, 다른 권한 처리, 다른 계산 로직, 다른 보안 수준, 다른 배포 방식을 갖기 시작하면 회사는 업무 자동화가 아니라 업무 파편화에 들어간다.

따라서 질문을 바꿔야 한다.

```text
나쁜 질문:
50개의 플러그인을 하나로 합칠 것인가?

좋은 질문:
무엇은 다양하게 두고, 무엇은 반드시 공통화할 것인가?
```

기준은 다음이다.

| 영역 | 허용해야 하는 것 | 공통화해야 하는 것 |
| --- | --- | --- |
| 화면, 단축키, 개인 작업 흐름 | 다양해도 됨 | 강제 통일 불필요 |
| 데이터 출처 | 개인 CSV 수준은 허용 | 운영 데이터는 표준 데이터 제품/API로 통제 |
| 계산 공식, 업무 규칙 | 개인 임시 실험은 허용 | 조직 KPI, 리스크 산식, 승인 기준은 공통화 |
| 권한, 인증, 로그 | 개인 도구도 최소 기준 필요 | SSO, RBAC, 감사 로그는 중앙화 |
| 배포 | 개인/팀 단위는 자유 | 전사 확산 시 ALM, 테스트, 보안 검토 필요 |

핵심 원칙:

> 50개의 UI는 괜찮다. 50개의 서로 다른 진실은 위험하다.

## 5. IT 부서의 역할 변화

IT 서비스 제공 부서는 앞으로 단순히 앱을 만들어주는 부서가 아니라 다음 역할로 이동해야 한다.

### 5.1 데이터 제공 부서

단순 데이터 마트 제공만으로는 부족하다.

앞으로 현업 AI 도구들은 CSV보다 더 좋은 데이터를 원한다.

- 권한이 적용된 API
- 검색 가능한 데이터 카탈로그
- 표준 지표
- 데이터 품질 정보
- lineage
- 데이터 계약
- 샌드박스 데이터
- AI 도구가 호출할 수 있는 업무 기능 API

Data Mesh의 기본 원칙은 도메인별 데이터 소유, 데이터의 제품화, 셀프서비스 데이터 플랫폼, 연합형 거버넌스다. 이 관점은 바이브코딩 시대의 데이터 제공 모델과 잘 맞는다.

### 5.2 내부 개발 플랫폼 제공 부서

현업 직원이 자유롭게 만들되, 안전한 길을 기본값으로 제공해야 한다.

Red Hat은 Golden Path를 조직 안에서 잘 문서화되고 지원되는 표준 개발/배포 경로로 설명한다. 중요한 점은 Golden Path가 강제 규칙이라기보다 사람들이 자연스럽게 선택하게 만드는 가장 쉬운 길이어야 한다는 점이다.

### 5.3 AI와 사내 시스템을 연결하는 도구 계층 제공자

Anthropic의 MCP는 AI 도구와 데이터 소스 사이의 연결을 표준화하려는 프로토콜이다. Anthropic은 MCP를 AI assistant와 데이터가 있는 시스템을 연결하기 위한 open standard로 설명한다.

앞으로 회사 데이터, 문서, CRM, ERP, 승인 시스템, 메일, 캘린더, 코드 저장소가 AI 에이전트의 도구가 된다.

그러면 IT의 핵심 일은 앱 개발보다 AI가 접근할 수 있는 안전한 도구/데이터 인터페이스를 만드는 일이 된다.

### 5.4 거버넌스와 운영 안정성 제공자

Microsoft Power Platform 쪽도 시민 개발을 관리하기 위해 CoE, 관리형 환경, 데이터 정책, ALM 같은 개념을 강조한다.

단, 2026-05-11 기준 Microsoft Learn의 CoE Starter Kit 문서는 해당 Starter Kit이 더 이상 actively maintained 되지 않으며, 핵심 기능은 Power Platform admin center에 포함되어 있다고 안내한다. 따라서 제품 문서나 영업 자료에서는 "CoE Starter Kit" 자체보다 "CoE/Center of Enablement 운영 모델, 관리형 환경, 데이터 정책, ALM"의 개념을 인용하는 편이 안전하다.

## 6. 하나로 합의해서 만들자는 방식의 한계

50명이 합의해서 하나의 서비스를 만들라고 하면 다시 과거 방식으로 돌아간다.

```text
회의
  -> 요구사항 조율
  -> 우선순위 충돌
  -> 타협안
  -> 느린 배포
  -> 일부 사용자 불만
  -> 다시 수정 요청
```

AI 시대에는 합의를 개발 전에 끝내는 방식보다, 먼저 만들고 실제 사용을 보고 공통 부분을 추출하는 방식이 더 맞다.

미래의 흐름은 이렇다.

```text
50명이 각자 만든다
  -> 사용량, 만족도, 오류율, 중복 기능을 관찰한다
  -> 비슷한 것들을 클러스터링한다
  -> 공통 데이터, 공통 로직, 공통 컴포넌트를 만든다
  -> 각자 다시 가져다 쓴다
```

합의의 위치가 바뀐다.

| 과거 | 미래 |
| --- | --- |
| 만들기 전에 합의 | 만든 뒤 사용 데이터로 수렴 |
| 하나의 전사 서비스 | 공통 코어 + 여러 변형 |
| 요구사항 회의 중심 | 실험, 사용량, 포크, 리믹스 중심 |
| IT가 제품 오너 | 현업이 마이크로 제품 오너 |
| 배포 전 승인 | 위험도별 자동 가드레일 |

이 방식은 오픈소스 생태계와 비슷하다. 모두가 각자 만들 수 있지만, 좋은 것은 재사용되고, 자주 쓰이는 것은 표준이 되고, 위험한 것은 플랫폼에서 막힌다.

## 7. 다음 단계와 다다음 단계

### 7.1 1단계: 개인 자동화 폭발

직원들이 자기 업무의 작은 불편을 계속 자동화한다.

예시는 다음과 같다.

- 엑셀 변환기
- 보고서 생성기
- 메일 요약기
- 데이터 정리 도구
- 내부 문서 검색기
- 회의록 정리기
- 특정 양식 생성기

이 단계에서는 중복이 많다. 하지만 조직은 이걸 너무 빨리 통제하면 안 된다. 이 단계의 가치는 숨은 업무 병목을 발견하는 것이다.

위험은 유지보수 불능이다. 만든 사람만 알고, 퇴사하면 사라지고, 데이터가 바뀌면 망가지고, 팀원이 쓰기 시작하면 비공식 핵심 시스템이 된다.

### 7.2 2단계: 데이터 요구 폭발

직원들은 곧 CSV 대신 실제 데이터를 붙이고 싶어 한다.

이때 IT의 역할은 앱을 만들어주는 것보다 안전하게 가져다 쓸 수 있는 데이터 제품을 제공하는 것이다.

필요한 제공물:

| 제공물 | 의미 |
| --- | --- |
| 데이터 카탈로그 | 어떤 데이터가 있는지 검색 가능 |
| 표준 지표 사전 | 매출, 고객, 이탈률, 리스크 등 정의 통일 |
| 권한 기반 API | 사용자의 권한에 따라 데이터 제공 |
| 행/열 수준 보안 | 부서, 직급, 역할별 접근 제한 |
| 데이터 품질 정보 | 최신성, 결측률, 신뢰도 표시 |
| 데이터 계약 | 필드명, 타입, 의미, 변경 절차 명시 |
| 샌드박스 데이터 | 실험용 익명화/가명화 데이터 |
| AI 도구 인터페이스 | MCP/API로 AI 에이전트가 안전하게 호출 |

이 단계부터 아무나 DB에 붙는 것은 막아야 한다. 대신 누구나 안전한 데이터 제품을 가져다 쓰는 것은 열어야 한다.

### 7.3 3단계: 내부 앱 마켓플레이스

50개의 플러그인을 없애는 것이 아니라 보이게 만들어야 한다.

사내 카탈로그는 다음을 보여줘야 한다.

- 누가 만들었는가?
- 어떤 데이터를 쓰는가?
- 누가 사용 중인가?
- 마지막 업데이트는 언제인가?
- 비슷한 도구는 무엇인가?
- 위험도는 어느 정도인가?
- 재사용 가능한 컴포넌트가 있는가?

중복 제거는 회의로 하지 않는다. 마켓플레이스에서 사람들이 많이 쓰는 도구가 드러나고, 비슷한 도구들이 묶이고, 일부는 공식화된다.

### 7.4 4단계: AI 에이전트가 개발자 역할 일부를 가져감

코딩 에이전트는 이미 단순 자동완성을 넘어가고 있다.

OpenAI Developers 문서 기준 Codex web은 코드를 읽고, 수정하고, 실행할 수 있는 OpenAI의 coding agent이며, cloud 환경에서 백그라운드 작업과 병렬 작업을 할 수 있다.

GitHub Docs 기준 Copilot coding agent도 GitHub Actions 기반의 자체 ephemeral development environment에서 코드를 탐색하고, 수정하고, 테스트/린터를 실행하며, 작업 결과로 pull request를 만든다.

회사 안에서는 현업 직원이 이렇게 요청하게 된다.

```text
이 고객군만 필터링해서 매주 월요일 담당자에게 예외 목록을 보내는 도구 만들어줘.

이 승인 프로세스에서 3일 이상 멈춘 건을 감지해서 요약하고, 사유 입력 폼을 만들어줘.

이 플러그인을 우리 팀 양식에 맞게 바꾸고, 보안 정책에 맞는지 검사해줘.
```

AI가 구현하고, 플랫폼이 배포하며, 사람은 의도와 예외를 관리한다.

### 7.5 5단계: 앱보다 업무 능력이 중요해짐

더 먼 단계에서는 개별 앱의 의미가 약해진다.

직원은 "플러그인 A"나 "웹서비스 B"를 만들기보다 이렇게 말한다.

```text
이번 주 리스크 높은 계약만 뽑아서 검토 화면 만들어줘.

이 데이터 기준으로 고객별 액션 플랜을 만들고, 담당자에게 보낼 초안을 준비해줘.

이 업무를 매번 반복하지 않게 자동화해줘. 다만 최종 승인은 내가 하게 해줘.
```

그러면 AI가 그 순간에 필요한 화면, 쿼리, 워크플로, 알림, 보고서를 생성한다.

이때 회사가 보유해야 하는 진짜 자산은 앱이 아니다.

진짜 자산은 다음이다.

- 데이터
- 업무 규칙
- 권한 체계
- 감사 로그
- 표준 API
- 조직 지식

### 7.6 6단계: 자기 진화하는 조직 운영체계

가장 멀리 보면 회사 안의 AI는 직원이 시키는 도구만 만드는 것이 아니라, 업무 패턴을 관찰하고 제안한다.

```text
이 팀의 17명이 비슷한 보고서 자동화 도구를 따로 만들고 있습니다.
공통 템플릿으로 묶을 수 있습니다.

이 5개 플러그인은 같은 데이터를 다른 방식으로 해석하고 있습니다.
표준 지표 정의가 필요합니다.

이 자동화는 고객 개인정보를 외부 API로 보낼 위험이 있습니다.
차단하거나 승인 절차가 필요합니다.

이 팀의 수작업 승인 지연이 반복되고 있습니다.
예외 처리 에이전트를 만들 수 있습니다.
```

이 단계에서 IT는 코드를 직접 많이 쓰는 조직이 아니라, 조직의 디지털 신경망을 설계하고 감시하는 조직이 된다.

## 8. 여러 미래 시나리오

### 8.1 시나리오 A: 방치형 미래

직원들이 각자 만들고, 회사는 모른다.

처음에는 생산성이 올라간다. 그러나 시간이 지나면 문제가 생긴다.

- 개인 계정으로 외부 AI 도구를 쓴다.
- 사내 데이터가 외부로 나간다.
- 같은 업무 기준이 다르게 계산된다.
- 만든 사람이 사라진다.
- 누가 어떤 자동화를 돌리는지 알 수 없게 된다.

이 시나리오에서는 결국 사고가 난 뒤 강한 통제가 들어오고, 현업은 다시 우회한다. 최악의 패턴이다.

OWASP는 LLM 애플리케이션 위험으로 prompt injection, insecure output handling, supply chain vulnerabilities, sensitive information disclosure, insecure plugin design, excessive agency, overreliance 등을 제시한다. 이는 AI 도구를 금지하라는 뜻이 아니라, AI 기반 내부 도구에도 위험 관리 체계가 필요하다는 뜻이다.

### 8.2 시나리오 B: 회귀형 미래

회사가 놀라서 모든 내부 개발을 승인제로 묶는다.

표면상 질서는 생기지만 바이브코딩의 장점은 사라진다.

현업은 다시 기다려야 하고, 작은 문제는 해결되지 않고, 몰래 만드는 도구가 생긴다. 기존 IT 병목의 반복이다.

### 8.3 시나리오 C: 플랫폼형 미래

가장 바람직한 방향이다.

개발은 현업이 한다. 하지만 데이터, 인증, 권한, 배포, 로그, 보안, 표준 컴포넌트는 플랫폼이 제공한다.

이 구조에서는 50명이 50개를 만들어도 괜찮다. 50개가 같은 인증, 같은 데이터 제품, 같은 배포 파이프라인, 같은 감사 체계, 같은 보안 정책 위에서 돌아가기 때문이다.

### 8.4 시나리오 D: 내부 앱 생태계 미래

사내에 앱스토어 같은 구조가 생긴다.

직원이 만든 도구가 등록되고, 다른 사람이 가져다 쓰고, 포크하고, 개선하고, 평가한다. 인기 있는 도구는 CoE나 IT 플랫폼팀이 지원해서 공식 도구로 승격시킨다. 덜 쓰이는 도구는 개인 생산성 도구로 남는다.

이 방식에서는 합의해서 하나 만들기보다 많이 쓰이는 것이 표준으로 올라가는 것이 중요하다.

### 8.5 시나리오 E: 앱 소멸 미래

가장 급진적인 미래다.

직원은 더 이상 플러그인을 만들지 않는다. AI 업무 에이전트에게 말한다.

```text
내가 매주 하는 이 일을 다음부터 대신 준비해줘.
```

그러면 에이전트가 필요한 데이터에 접근하고, 임시 UI를 만들고, 승인 요청을 보내고, 기록을 남긴다.

이때 앱은 영구 자산이 아니라 특정 업무 순간에 생성되는 인터페이스가 된다.

통제점도 바뀐다.

| 과거 | 미래 |
| --- | --- |
| 앱 통제 | 에이전트 권한 통제 |
| 화면 통제 | 데이터, 행동, 감사 통제 |
| 코드 리뷰 | 정책, 시뮬레이션, 로그 리뷰 |

## 9. 회사가 설계해야 할 운영 모델

핵심은 위험도별 구분이다. 모든 도구를 똑같이 다루면 실패한다.

| 레벨 | 예시 | 허용 방식 |
| --- | --- | --- |
| 레벨 1: 개인 샌드박스 | 내 보고서 변환기, 개인 CSV 정리 도구 | 자유롭게 허용. 회사 데이터 업로드 금지, 외부 공유 금지, 자동 배포 금지 |
| 레벨 2: 팀 도구 | 팀 업무 현황판, 팀별 정산 도구 | 등록, 공유, 기본 검토, 소유자 지정 |
| 레벨 3: 부서 운영 도구 | 부서 승인 자동화, 부서 KPI 대시보드 | ALM, 권한, 로그, 운영 책임자, 변경 승인 |
| 레벨 4: 전사 핵심 시스템 | 매출 산정, 고객 통지, 법적 보고, 인사/재무 | 공식 시스템 수준 관리, IT/보안/데이터팀 공동 소유 |

Microsoft는 시민 개발자가 만든 앱과 흐름을 건강한 ALM 모델로 이동시키는 것을 권장하며, 공유 컴포넌트나 에이전트를 배포할 경우 개발, 테스트, 릴리스 환경을 분리하는 모델을 설명한다.

## 10. 50개의 플러그인 문제에 대한 구체적 해법

### 10.1 모든 도구를 등록하게 한다

처음부터 승인제가 아니라 가시화부터 해야 한다.

등록 항목은 간단해야 한다.

- 이름
- 만든 사람
- 사용자 수
- 쓰는 데이터
- 외부 연결 여부
- 업무 중요도
- 마지막 실행일
- 공유 범위

처음부터 복잡하게 하면 아무도 등록하지 않는다.

### 10.2 데이터 접근은 표준 경로로 제한한다

개인 도구가 운영 DB에 직접 붙으면 안 된다.

대신 다음 경로를 제공해야 한다.

- 회사가 제공하는 데이터 제품
- 권한 기반 API
- MCP 서버
- 승인된 커넥터
- 샌드박스 데이터셋

IT의 경쟁력은 막는 능력이 아니라, 안전한 경로가 비공식 경로보다 훨씬 편하게 만드는 능력이다.

### 10.3 중복 도구를 클러스터링한다

50개를 일일이 심사하지 말고 AI가 자동으로 묶게 할 수 있다.

클러스터링 기준:

- 같은 데이터 사용
- 같은 기능 설명
- 비슷한 화면
- 같은 업무 단계
- 같은 산출물
- 같은 사용자 집단

그 다음 공통 기능을 추출한다.

### 10.4 공통 코어와 개인화 UI를 분리한다

예를 들어 50명이 모두 고객 우선순위 산정 플러그인을 만들었다고 하자.

나쁜 방식은 50개를 하나로 통합하는 것이다.

좋은 방식은 이렇다.

```text
고객 데이터 제품은 하나
우선순위 산식은 하나 또는 버전 관리
권한 체계는 하나
UI는 여러 개
알림 방식은 팀별 선택
필터와 보기 방식은 개인화
```

원칙:

> 업무의 진실은 하나로, 사용 경험은 다양하게.

### 10.5 많이 쓰이는 것은 공식화한다

일정 기준을 넘으면 개인 도구가 아니라 제품 후보가 된다.

승격 기준 예시:

- 사용자 20명 이상
- 월 100회 이상 실행
- 부서 핵심 업무 연결
- 민감 데이터 사용
- 오류 발생 시 업무 중단
- 외부 발송 기능 포함

### 10.6 폐기와 책임 이전도 제도화한다

내부 도구가 늘어나면 만드는 것보다 버리는 것이 더 중요해진다.

필요한 정책:

- 90일 미사용 도구 자동 알림
- 소유자 퇴사 시 인수인계
- 위험 도구 자동 차단
- 비슷한 공식 도구가 생기면 마이그레이션 권고
- 오래된 데이터 커넥터 만료

이게 없으면 사내는 죽은 자동화로 가득 찬다.

## 11. 데이터 제공 서비스 설계

데이터 제공은 데이터 마트 만들어주기로 끝나면 안 된다.

AI 시대의 데이터 제공은 세 층으로 나뉜다.

### 11.1 1층: 신뢰 가능한 데이터

여기에는 데이터 마트, 데이터 웨어하우스, 데이터 레이크, 마스터 데이터, 표준 지표가 포함된다.

하지만 이것만 있으면 현업은 여전히 어렵다.

### 11.2 2층: 사용 가능한 데이터 제품

현업과 AI가 바로 쓸 수 있어야 한다.

예시는 다음과 같다.

| 기존 표현 | 제품화된 표현 |
| --- | --- |
| 고객 목록 테이블 | 권한이 적용된 고객 검색 API |
| 계약 테이블 | 계약 리스크 조회 도구 |
| 매출 테이블 | 표준 매출 지표 서비스 |
| 프로젝트 DB | 프로젝트 상태/리스크/담당자 조회 API |

### 11.3 3층: AI 에이전트용 도구

AI에게 테이블만 주면 위험하다.

AI에게는 무엇을 할 수 있고 무엇을 하면 안 되는지가 명확한 도구가 필요하다.

예시:

```text
search_customer()
get_sales_summary()
check_contract_risk()
create_draft_email()
submit_approval_request()
log_decision_reason()
```

각 도구에는 권한, 제한, 로그, 검증 규칙이 붙어야 한다.

미래의 데이터팀은 SQL 테이블만 제공하는 팀이 아니라, AI와 사람이 안전하게 호출할 수 있는 업무 기능 API를 제공하는 팀이 된다.

## 12. 문화 변화

가장 큰 변화는 개발이라는 단어의 의미다.

과거에는 개발이 프로젝트였다.

미래에는 개발이 업무 중 일부가 된다.

### 변화 1: 직원은 사용자에서 제작자로 바뀐다

직원은 더 이상 요청자만이 아니다. 자기 업무를 설명하고, 도구를 만들고, 개선하고, 공유하는 사람이 된다.

### 변화 2: IT는 해결사에서 플랫폼 운영자로 바뀐다

IT가 모든 문제를 직접 해결하지 않는다. 대신 남들이 해결할 수 있는 환경을 만든다.

### 변화 3: 기획 문서보다 프로토타입이 먼저 온다

"이런 게 필요합니다"라고 문서 쓰는 대신, "이렇게 만들어봤는데 팀에서 쓰게 해도 되나요?"가 된다.

### 변화 4: 표준화는 사전 합의가 아니라 사후 수렴이 된다

처음부터 하나로 정하지 않는다. 여러 개가 생기고, 사용 데이터를 보고, 좋은 것을 표준화한다.

### 변화 5: 보안은 승인 부서가 아니라 자동 가드레일이 된다

사람이 일일이 승인하면 속도를 따라갈 수 없다. 정책은 코드화되고, 배포 파이프라인과 데이터 커넥터에서 자동 적용되어야 한다.

## 13. 설계 원칙

핵심 원칙:

> 창작은 분산시키고, 신뢰는 중앙화한다.

구체적으로는 다음과 같다.

| 분산시킬 것 | 중앙화할 것 |
| --- | --- |
| 아이디어 | 인증 |
| 화면 | 권한 |
| 개인 워크플로 | 데이터 정의 |
| 프로토타입 | 감사 로그 |
| 실험 | 보안 정책 |
| 작은 자동화 | 배포 파이프라인 |
| 업무별 변형 | 표준 API |
| 프롬프트와 UX | 핵심 업무 규칙 |

이 구조를 만들면 50개의 플러그인은 위험이 아니라 자산이 된다.

반대로 이 구조가 없으면 50개의 플러그인은 통제 불가능한 shadow IT가 된다.

## 14. 가장 그럴듯한 미래

가장 현실적인 미래는 다음이다.

> 회사는 하나의 전사 앱을 만들지 않는다. 대신 하나의 전사 플랫폼을 만든다.

그 플랫폼 위에서 직원들은 계속 자기 도구를 만든다.

하지만 그 도구들은 모두 같은 데이터 제품, 같은 권한 체계, 같은 배포 경로, 같은 로그 체계, 같은 보안 정책을 사용한다.

사내 소프트웨어 구조는 이렇게 된다.

```text
맨 아래: 데이터 플랫폼
  -> 표준 API, MCP, 업무 기능 도구
  -> 권한, 정책, 로그, 배포 파이프라인
  -> 현업이 만든 수많은 앱, 플러그인, 에이전트
  -> 직원별 개인화된 업무 경험
```

이 구조에서는 50개가 만들어지는 것이 문제가 아니다.

문제는 50개가 서로 다른 진실과 서로 다른 위험을 갖는 것이다.

질문은 이렇게 바뀌어야 한다.

| 과거 질문 | 미래 질문 |
| --- | --- |
| 누가 만들었는가? | 어떤 데이터와 권한으로 움직이는가? |
| 하나로 합칠 것인가? | 공통 코어는 무엇이고, 개인화해도 되는 부분은 무엇인가? |
| IT가 만들어줄 것인가? | IT가 어떤 플랫폼을 제공해야 현업이 안전하게 만들 수 있는가? |
| 개발을 통제할 것인가? | 위험한 행동만 자동 통제하고, 나머지는 열어둘 수 있는가? |

## 15. 지금 당장 취할 현실적 대안

1. 사내 바이브코딩 원칙을 만든다.
   금지가 아니라 기준이다. 개인 도구, 팀 도구, 운영 도구, 전사 도구를 구분한다.

2. 모든 내부 도구 등록소를 만든다.
   승인제가 아니라 인벤토리부터 시작한다.

3. 데이터 접근 표준 경로를 만든다.
   CSV 다음 단계는 데이터 마트만이 아니라 API, 데이터 제품, 권한 기반 커넥터다.

4. 개인 샌드박스와 운영 환경을 분리한다.
   개인 실험은 자유롭게, 운영 배포는 파이프라인을 타게 한다.

5. 중복 제거 회의를 하지 말고 중복 탐지 시스템을 만든다.
   AI로 유사 도구를 묶고, 많이 쓰이는 것을 공식화한다.

6. 공통 컴포넌트 라이브러리를 만든다.
   인증, 테이블 조회, 차트, 승인 요청, 메일 발송, 로그 기록 같은 것은 재사용 가능해야 한다.

7. CoE 또는 Enablement Team을 만든다.
   이름은 중요하지 않다. 통제 조직이 아니라 현업 제작자를 키우고 위험을 낮추는 조직이어야 한다.

8. 인기 있는 현업 도구를 공식 제품으로 승격시키는 절차를 만든다.
   이게 없으면 좋은 도구도 개인 프로젝트로 남고, 나쁜 도구도 계속 퍼진다.

## 16. 내부 플랫폼이 제공해야 할 기능

이 문화 변화에 대응하려면 내부 플랫폼은 다음 기능을 가져야 한다.

| 기능 | 이유 |
| --- | --- |
| 앱/플러그인 등록소 | 무엇이 존재하는지 보이게 함 |
| 사용자/팀/부서 소유자 관리 | 책임 소재 명확화 |
| 데이터 제품 카탈로그 | 운영 DB 직접 접근 방지 |
| 권한 기반 API/MCP | AI와 사람이 안전하게 데이터 호출 |
| 표준 템플릿 | 현업이 안전한 기본값으로 시작 |
| GitLab CI/CD 자동화 | 배포 경로 표준화 |
| Nginx/도메인/인증서 자동화 | 내부망 접속 경로 표준화 |
| 감사 로그 | 누가 무엇을 만들고 배포했는지 추적 |
| 위험도 분류 | 개인/팀/부서/전사 도구를 다르게 관리 |
| 중복 탐지 | 비슷한 도구를 클러스터링 |
| 공식화 워크플로 | 인기 도구를 제품 후보로 승격 |
| 폐기/인수인계 | 죽은 자동화와 소유자 공백 방지 |

## 17. 제품 관점의 기회

이 변화는 내부 개발 플랫폼 제품의 기회를 만든다.

제품의 메시지는 다음이어야 한다.

> 바이브코딩을 막는 보안 솔루션이 아니라, 바이브코딩을 사내 표준 경로 안으로 흡수하는 플랫폼.

제품은 단순 GitLab/Nginx 설치기가 아니라 다음을 제공해야 한다.

- 사내 앱 생성 포털
- 관리 대시보드
- GitLab 기반 repo/CI/CD 자동화
- Ubuntu/Nginx 기반 내부망 배포
- 인증서 자동화
- 데이터 제품/API/MCP 연계
- 앱 카탈로그
- 소유자와 사용량 관리
- 위험도 기반 배포 정책
- 감사 로그
- 중복 탐지와 공식화 흐름

즉, 제품의 본질은 "사내망용 AI 앱 팩토리 + 거버넌스 플랫폼"이다.

## 18. 한 문장 정리

앞으로 회사의 내부 소프트웨어 문화는 다음 방향으로 간다.

> IT가 만들어주는 시대에서, 모두가 만들고, 플랫폼이 통제하고, AI가 구현하고, 데이터가 중심이 되는 시대로 간다.

정답은 50개의 플러그인을 막는 것이 아니다.

정답은 다음이다.

> 50개의 플러그인이 생겨도 회사의 데이터 정의, 권한, 보안, 감사, 운영 안정성은 하나의 체계 안에 남아 있게 만드는 것.

그것이 앞으로 IT 부서와 데이터 부서가 해야 할 일이다.
